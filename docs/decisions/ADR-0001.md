# ADR-0001 — Monorepo for Palette Canvas Foundation

**Status:** Accepted  
**Date:** 2026-08-21  
**Owner:** Engineering lead

## Context

The planning document (section 2, "End-to-end production workflow", and section 6,
"Recommended core modules") requires a TypeScript-first modular monolith:
Next.js for the workspace experience, NestJS for the domain API, and a design-system
foundation for consistent UI. The document further mandates a `workspaces`
structure and explicit permission/tenancy rules from day one.

The earlier Phase 1 prototype (`prototypes/color-tool`) is a clickable color-workspace
artifact retained for reference; it does not form the foundation.

## Decision

Use npm workspaces to structure the monorepo:

- `apps/web` — Next.js workspace shell
- `apps/api` — NestJS foundation (audit + permission services)
- `packages/shared` — types, `VisibilityLevel`, `Role`, `canSeeVisibility`
- `packages/design-tokens` — colors/typography/spacing as single source
- `prototypes/color-tool` — preserved Phase-1 prototype (reference)

The `apps/*` and `packages/*` build together during the CI quality gate
(`scripts/check-gates.sh`).

## Consequences

- Shared types enforce consistent role/visibility semantics across web and API
- Design tokens are versioned with the repo and consumed by the web shell
- Permission logic lives in `packages/shared` for now; Phase 2 moves enforcement
  to Postgres-backed stores in `apps/api`

## Alternatives considered

- Single Vite/React SPA + separate backend — rejected because the plan prescribes
  Next.js + a modular monolith with explicit domain boundaries
- Polyrepo — rejected: shared types make that expensive and brittle at this stage
