# ADR-0002 — Open infrastructure decisions gating the A-block

**Status:** Proposed — awaiting human decision
**Date:** 2026-09-15
**Owner:** Product owner / engineering lead (human), not an agent

## Context

The V2 phases (boards, comms, dashboards, agents, public surface) are complete
and merged, and V2 Phase 6 has been corrected against the authoritative
specification package. What remains is the A-block (`docs/roadmap.md` Phase 9).
Four of its slices are **not** blocked on engineering — they are blocked on
decisions that `AGENTS.md` explicitly reserves for humans:

> Platform/N/A entries are only closable by a human; the agent records them in
> the ledger but does not choose infrastructure.

Three of these decisions gate a long dependency chain, so leaving them implicit
is currently the largest source of stalled work. This ADR makes them explicit
and dated, so they can be resolved rather than rediscovered each session.

## Decisions required

### D1 — Email transport provider (§0.2)

**Blocks:** only the delivery step. The seam, the token model and the hardened
flows are now built and green without a provider — see the resolution note below.

**Options:** SMTP relay · Resend · SES · a fourth.

**Question for the human:** which provider, and is the dev fallback (rows
written to `email_outbox`, sends logged not delivered) acceptable for the pilot?

**Resolution note (N1.1, 2026-09-15):** the abstraction is in place —
`apps/api/src/email/email.transport.ts` defines `EmailTransport`, with an
`OutboxOnlyTransport` default and an SMTP implementation selected by
`PC_SMTP_HOST`/`PC_SMTP_FROM`. `EmailService` separates durable enqueue (inside
the caller's transaction) from best-effort dispatch (after commit, never
throws). The provider choice is therefore now configuration, not code.

**Open gap this leaves:** with no provider, the outbox row *is* the delivery
channel, so `email_outbox.body` has to carry the plaintext token for an operator
to read. The `token_hash` at-rest protection is therefore cosmetic in this
configuration. When a provider is selected, the body should be rendered from the
token at dispatch time instead of stored. This is a real (accepted, temporary)
weakness, not a solved problem.

### D2 — Hosting region (§15.2, `render.yaml`)

**Blocks:** the residency wording on the privacy page. `render.yaml` exists with
no region pinned. The user has directed Render as the deployment host (this
supersedes the specification package's AWS `af-south-1` instruction — recorded
as a substitution, per the package's own instruction to surface rather than
silently follow).

**Question for the human:** which Render region? This is also the input to D3,
because the PIPEDA-relevant question is whether UK Partner Agency data can leave
the UK at all under the UK GDPR/POPIA reading.

### D3 — UK GDPR vs POPIA applicability for UK Partner Agency data

**Blocks:** legal finalisation of the privacy page (A-16 adjacent; the page ships
as a draft with an explicit counsel-review caveat and an open-item marker).

The specification package flags this itself, in `README.md`:

> The Privacy Policy's UK GDPR question (does UK GDPR apply alongside POPIA for
> UK Partner Agency data, given the UK subdomain shares this same platform) —
> needs your decision and likely legal review.

**Question for the human:** does UK GDPR apply alongside POPIA, and does that
constrain D2? An agent must not answer this. The page currently states the
question rather than asserting an answer.

### D4 — Storage backend and LLM provider host

Both already have built seams (`apps/api/src/storage`, `apps/api/src/llm`), both
no-op without configuration, and both are correctly reported as unconfigured in
the UI. Lower priority than D1–D3 because nothing is blocked on them yet; listed
so they are not lost.

## Consequences

- Until D1 is answered, no A-block engineering work can start on the identity
  chain. N2 (board/comms frontend) and N3.4 (drill refresh) are the
  highest-value work that does **not** depend on D1–D3 and can proceed now.
- Until D2/D3 are answered, the privacy page carries an open-item marker. That
  is the correct state, not a gap to paper over: an invented answer is worse
  than a flagged unknown, and invented legal content has already had to be
  retracted once in this repository (see the SPA rows in the ledger).
- Once answered, each decision is recorded here with a date and an owner, and
  the affected ledger row moves from `blocked` to `todo`.

## Alternatives considered

- **Agent picks sensible defaults and marks them "configurable".** Rejected:
  `AGENTS.md` forbids it for infrastructure, and a residency default silently
  becomes a legal claim.
- **Defer all four until the pilot.** Rejected for D1 — it converts a
  one-line human answer into a multi-week stall on the largest remaining
  dependency chain.
